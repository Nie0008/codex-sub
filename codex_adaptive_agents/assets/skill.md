# 子代理协作

主 Agent 对齐目标、选择分工、协调依赖、检查关键证据并整合交付。具体执行与专业核验都可委派；主 Agent 不因主控身份就更擅长验收，也不必重复全部检查。目标是在任务质量满足要求的前提下减少账号总消耗；计入交接、复核、重试和返工，不以原始 token 或模型单价单独判断收益。

用户指定的执行者、模型、流程、预算和项目约定优先。只在已有任务授权与宿主实际支持的范围内委派；同一可写工作单元只交给一个执行负责人，真实执行与验收如实记录。

以下协作方式、模式和方法是可调整的起点。按任务组合、跳过、改变顺序、替换或采用其他合适方法；人数、轮次和交付形式随实际需要安排，同时遵守已指定的边界。探索包可以围绕问题与未知交接，不要求事先确定最终方案；未验证的设想标为假设，成为交付事实或行动依据时再核查重要前提。

## 选择执行方式

| 条件 | 优先做法 |
| --- | --- |
| 小修改、主要是主控判断、依赖当前上下文且交接成本高 | 主 Agent 直接完成 |
| 目标、产物归属、材料和验收明确；宿主内有可用原生 Agent | 交给合适的原生 Agent，已有 Luna 档位是候选之一 |
| 需要 Workbench 已接入的执行器或模型，或它的任务管理、续办能力有实际价值 | 按需调用现有 agent-workbench-dispatch Skill |
| 有影响目标、核验或共享写入的关键缺口 | 补必要材料或确定边界；能独立推进的探索与检查继续 |

这些条件不是排他分类。候选都可行时，比较任务能力、可交接性、已有质量证据、可获得的成本及复核负担；没有测量就记录未知。文件数量、篇幅、coding 标签、任务时长不直接决定通道或档位。小任务不为收集样本强行委派；独立工作才并行。

具体档位条件、例子、失败处理和记录协议见安装目录下的 `../../codex-adaptive-agents/runtime/docs/CODE_SCENE.md`；在源码中阅读本模板时对应 `../../docs/CODE_SCENE.md`。实际选择时按需读取对应部分。

按当前任务确定验收：代码检查受影响行为，研究核对来源与覆盖范围，写作按读者和用途通读，数据处理核对口径与可复算结果。引用已有专业 Skill 和项目规则；不因任务标签强制套用方法或固定角色。

## 选择协作方式

根据覆盖缺口、关键结论的独立核查需要、可分开的工作及交接成本选择，可在执行前安排多方，不必等失败再追加。

| 需要 | 可采用的方式 |
| --- | --- |
| 结果能直接检查，增加参与者没有明确贡献 | 直接完成或单个执行者 |
| 有互不阻塞的工作或不同材料范围 | 并行分工，关键交界处再交叉核查 |
| 核心事实、计算、实现或文档结论需要独立证据 | 独立交叉验证，复核者按任务设计检查和返回证据 |
| 多种合理取舍或相互依赖的约束需要讨论 | 圆桌：分别形成观点或共同梳理约束，再讨论具体分歧 |
| 需要发现新方向、尚未收敛候选 | 头脑风暴：独立发散、共同探索或接续创意，再按目标和约束筛选 |
| 已有方案，但关键假设或失败机制未验证 | 对抗性分析或方案对比；围绕可检验的疑点工作 |

分工覆盖不同部分，交叉验证独立核查关键重叠部分；两者可组合。人数、角色和模型由实际缺口与能力决定。不同角色、通道或模型不自动构成独立证据。需要检验独立判断时，先给同样的必要原材料，不先灌输另一方答案；共同探索允许提前交流，成果不冒充独立验证。审查产物则提供实际产物及验收依据。

每方可以在自己的归属内创建报告、测试或候选方案。核验者不同时修改被核验的共享产物；修复默认交回原 owner，明确阶段交接且原 owner 已停止写入时也可移交。主 Agent 回查决定结论的证据，分歧靠来源、计算或试验处理，不按票数裁决。关键疑点已处理，或下一轮不能增加有用证据、解释、候选或可执行选项时收口；缺事实就保留未知。

需要多轮协作时，先明确本轮要解决的分歧及合适的时间、轮次或用量边界；到界限交付已知与待查，不能因尚未共识无限续聊。预算缺少账单依据时不宣称精确金额上限。

需要拆假设、换视角或设计验证时，按需读取安装目录旁的 `../think/SKILL.md`；在源码中阅读本模板时对应 `think/SKILL.md`。分析、设计、脑暴、执行与审计的常用组合见上述使用说明，可调整或采用清单外的方法。think 可独立使用；不可用时仍按任务完成必要分析。

## 执行与记录

- 派发材料写清目标、必要来源、绝对目录、归属、产物和验收；引用已有项目规则和相关 Skill。
- 子代理默认完成收到的工作包；主 Agent 可在已有用户委派授权与宿主能力内明确允许有限再分工，说明子包范围、归属、可用执行者与预算边界。每次派发核对工具和并发能力，记录父子包关系；原负责人协调、整合并交付，再分工不扩大权限或成本范围。
- 原生 Agent 使用宿主实际暴露的派发工具与候选。Luna 的 `adaptive_luna_low/medium/high/xhigh/max` 是已有五个推理档位；按需选择，不限定所有工作包都用 Luna。若角色不在宿主工具的可用候选中，不能假称派发成功。
- Workbench 使用已有 `agent-workbench-dispatch`：读取真实工具 schema、当前 Agent/供应商/模型组合及项目背景，再下发和等待关键事件。用户未指定模型时可用已保存默认，但必须回读实际执行组合。只交接相关材料，不建立第二套任务、凭据或项目记忆服务。
- 普通故障由当前 owner 处理；环境、权限、配额错误先按根因恢复。原任务状态不明先回读，不能直接另开执行者重复执行或修改同一产物。能力或范围确实变化时才停止旧写入并重新交接。
- 每个实质工作包实际开始后，用 `{{COMMAND}} code-record --project <绝对项目目录> --input <绝对JSONL路径> --purpose production` 保存选择理由、可行替代方案和真实执行标识。state 说明协作方式、分工、核查点及所用方法，evidence 引用独立产物与实际工具回执。执行结束再记录有证据的结果、返工、耗时和用量；未知留空。宿主未披露具体模型时填 model=unknown 并在证据中说明，不能猜成 Luna。问答和一次小改不强制登记。
- Laya 保持派发后的旁路测试。已有代码场景的原生 Luna 工作包可用同一入口的 `code-shadow`，实际选择和事后结果不进入模型输入。其他场景及主 Agent、Workbench 使用通用的 `code-record` 记录；该命令名沿用已有接口，不限制任务类型。当前没有经过验证的非代码或跨通道 Laya 预测。
- 核对实际产物和必要验证，不用执行方自述替代验收。向用户简要报告执行者、选择理由、产物和真实验证；配置安装、实际模型执行及账号节省分别说明。
