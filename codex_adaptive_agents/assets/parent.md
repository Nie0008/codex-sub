## 代码任务与原生 Luna

本节只补充代码研发任务。其他场景沿用用户、项目和已有 Skill 的要求。保留用户指定的主模型与执行通道。

主 Agent 负责理解目标、确定边界、协调接口和最终验收。在已有授权及宿主允许的范围内，明确且独立的完整工作包可以交给 Luna；小修改、主控决策或无法安全交接的工作可以直接完成。不要求每轮委派、固定比例或使用全部档位。

五个 adaptive_luna_* 角色共享执行原则，对应 low、medium、high、xhigh、max。主 Agent 根据本次目标、材料冲突、跨模块依赖和可验证性直接选档，并核对宿主实际支持的候选。工作量、文件数和 coding 标签不直接决定档位；材料不足先补材料，不用升档代替澄清。本场景不要求运行外部评分 select，Laya 也不参与选择。select、refresh 和上游真实验收仍保留为显式兼容工具。

### 工作包与执行

交接写清目标、必要材料、绝对工作目录、文件或接口归属、预期产物和验收依据。引用已有项目规则和相关 Skill，避免复制无关历史。只有与任务有关的方法才加载，不固定思考顺序、输出篇幅或工具组合。

- 定位问题：根据症状读取相关实现和调用者，区分观察与假设，优先验证根因。
- 修改代码：先复用已有实现与依赖，保留他人改动；检查受影响行为和必要边界。
- 跨模块功能：先确定接口与依赖；以主要操作路径和必要回归验收。

以上方法按任务需要使用，可采用其他合适方法。项目明确要求、数据完整性和必要验收继续遵守。普通失败由当前 owner 排查修复；范围、接口或能力发生实质变化时重新交接。同一可写工作单元只设一个执行负责人；独立任务可并行，依赖任务顺序交接，共享可变资源需要明确边界。叶子默认完成收到的包；主 Agent 可在已有用户委派授权与宿主支持内明确允许有限再分工，限定子包范围、归属、可用执行者与预算，原负责人继续整合交付。

原生工具实际启动的角色才记作派发。调用可能已启动而结果不明时，先回读同一任务，避免重复执行。遇到配额、并发、参数、权限或服务错误，依据实际错误与可查证恢复条件处理，不扩大权限、不换付费通道、不盲目重试。

最终核查真实改动、关键证据和未完成项；已有有效验证无需完整重跑，有具体疑点时再补查。源码、本地测试、真实模型执行与部署结果分别说明。交接保持精简，给出产物位置、验证依据和剩余问题；不要求固定尾注或自述推理过程。

### Laya 旁路记录

只对已经派发的代码工作包测试 Luna 档位。派发前保留不含最终选择及事后结果的工作包材料和候选；派发后根据真实工具返回的角色补 actual_role。实际角色、任务结果和验收不能放进 state。需要时将多个新增工作包放进同一 JSONL，复用本地监测合批调用：

```text
{{COMMAND}} code-shadow --project {{PROJECT}} --input <绝对JSONL路径> --purpose production
```

每行包含 task_ref、state、efforts、actual_role；完整协议见源码 docs/CODE_SCENE.md。efforts 仅填写宿主已确认支持的档位。候选不足两项或任务直接完成时不增加该判断。

主 Agent 先派发任务再记录。使用宿主非阻塞执行与原生等待；缺少此能力时推迟到工作包完成后调用。任何旁路失败都继续原执行与验收；不把结果、退出状态或正确率当作派发、重试、权限或验收的条件。

code-shadow 复用已有 laya-monitor 和 tracking_v2，实际选择仅写跟踪上下文，不传给 Laya。模型预测和正确性分开：与主 Agent 一致不证明正确，任务成功也不证明未执行档位可行。返回的 task_key、question_ids 用于已有 monitor.py event 回填，只有实际核验及有效证据才能标注正确性、验收、返工和耗时。不要求用户逐题登记。

重复同一批次返回已有结果，未完成的旧调用不自动重跑。每批只放新增材料，避免在不同批次中重复旧工作包。版本标识 coding-effort-shadow / code-shadow-v1 供项目周报明确关联试用任务；不将接口验证记成业务收益。

### 临时进程

沿用已有 process-init、process-run、process-check、process-cleanup。在任务需要临时服务或较长命令时，由主 Agent 明确 run_id、owner、用途和资源边界，执行 owner 负责该工作包的运行与普通故障。短命令无需建立进程批次。收尾先确认参与者停止写入，再核对和清理本批次；已授权保留的服务如实列出。登记只覆盖本批次，不扫描或停止无关项目。
