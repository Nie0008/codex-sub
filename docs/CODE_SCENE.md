# sub：选择执行者与记录结果

Codex Sub 的公开使用说明，独立维护于 Nie0008/codex-sub。

适用于代码、研究、写作、资料整理、数据处理等可交接任务。主 Agent 自行判断直接完成、使用宿主原生 Agent 或调用现有 Workbench，
并负责交接、关键证据与最终整合；具体核验可以委派。Skill 提供判断依据，脚本记录事实；没有一个独立程序自动替你决定执行通道。
目标是质量满足要求时降低账号总消耗，计入主控协调、交接、复核、重试和返工。

## 启用

使用 Python 3.11+。以下以 Python 3.12 为例，从这份本地源码执行：

```sh
python3.12 scripts/init.py --dry-run
python3.12 scripts/init.py --yes --plan-id <预检查返回的plan_id>
```

此模式添加 `skills/sub/SKILL.md`、`skills/think/`、五个 `agents/adaptive_luna_*.toml` 和
受管运行文件；不修改 `AGENTS.md`、`AGENTS.override.md`、默认主模型或默认子模型。
已有同名但非本安装器管理的文件会拒绝覆盖。安装有备份，卸载或回滚复用原入口。
保留原来的全局规则安装模式作为上游兼容工具；本地试用采用 `--skill`。
从旧版升级会在核对受管文件后移除旧的 code-collaboration 入口，保留事务备份；
旧目录内其他文件保持不动。

在新聊天中指定“用 sub 处理这个任务”或 `$sub`，也可由 Codex 根据 Skill 描述匹配。
sub 是 Skill 的入口名，没有新增 shell 命令。
实际可用角色以宿主返回为准，安装文件不等于角色已加载或模型已执行。
从安装返回的 `standalone_entrypoint` 运行 `doctor`，READY 只代表安装文件和本地入口检查通过；
原生模型访问、Workbench 派发和业务效果另行验证。

## 什么情况下选什么

先尊重用户指定的执行者和模型，核对已有授权与实际可用能力；然后看任务是否值得交接。

| 情况 | 初始选择 | 理由与边界 |
| --- | --- | --- |
| 已定位的一次小改、短查询、主控决策 | 主 Agent | 交接成本可能高于执行本身；不为样本数量开代理 |
| 关键决策依赖当前上下文，难以精简交接 | 主 Agent 先处理 | 先确定需求和接口，明确的后续工作再交出去 |
| 目标、材料、产物归属和验收明确，原生 Agent 可用 | 宿主原生 Agent 候选 | 当前宿主内交接方便；Luna 五档是已有候选之一 |
| 需要 Workbench 当前已接入的执行器或模型 | Workbench 候选 | 必须查询当前准确的 Agent/供应商/模型组合，不能按历史配置猜 |
| 任务管理、原任务续办或已有项目背景在 Workbench 有实际价值 | Workbench 候选 | 复用现有 taskId 和项目；任务长本身不代表必须用 Workbench |
| 两个以上候选都能完成 | 比较能力、交接和已有质量/成本证据 | 同等条件优先减少新增协调；没有成本证据不声称某通道更省 |
| 目标矛盾、材料不足、口径未定或共享写入归属不清 | 主 Agent 先补材料/定边界 | 升档和并行都不能替代这些工作 |
| 配额、权限、依赖、服务或工具参数错误 | 当前 owner 先诊断 | 先处理环境与状态；不因这类错误直接换更强模型 |

文件数、篇幅、场景标签和任务时长不能直接决定通道。涉及删除、权限或真实数据等操作时，
授权范围由已有用户要求和项目规则确定；模型更强或 confidence 更高不会增加授权。
用户明确指定的执行者不可用时说明具体缺项，不能悄悄换到另一供应商或付费通道。

典型例子：改一个已知函数的空值处理可以直接完成；边界明确且有现成验收的独立功能可交给 Luna；
用户指定 CC 配合某个已配置模型，或要续办 Workbench 原任务，则走 Workbench。
跨前后端任务先固定接口，两个不重叠的实现包才考虑并行，不按“前后端”字样自动开两个代理。
整理一份独立资料的来源与结论、按既定受众改写一篇文章、按明确口径清洗一张表，也可以成为工作包。
讨论目标或价值取舍仍由主 Agent 保持上下文；题材本身不指定执行通道。

## 不同任务怎么交接与验收

先明确这次产物服务谁、用于什么，按任务补齐最少的材料与验收条件。复用已有项目和专业 Skill，
不为每个场景建立一套固定流程。以下是起点，具体要求以当前任务为准：

| 任务 | 交接时说明 | 验收依据（具体核查可委派） |
| --- | --- | --- |
| 代码实现或修复 | 预期行为、相关实现与调用者、可写边界 | 受影响行为、必要边界与项目要求的检查 |
| 研究或资料整理 | 问题、来源范围、时点、输出用途 | 来源可回查、覆盖范围明确，事实与推断分开 |
| 写作或改写 | 读者、阅读场景、材料、读后目标 | 脱离聊天通读，内容自足、事实有依据、符合用途 |
| 数据整理或分析 | 字段含义、统计口径、允许的输入与输出 | 结果可复算，缺失与异常处理明确、汇总能核对 |

不确定性、约束之间的依赖、材料是否充分、错误能否直接检出，比任务描述长度更能说明判断难度。
专业任务需要对应能力和验收依据；没有这些条件时先补齐，不能用委派或升档代替。

## 执行、讨论与交叉验证怎么组织

工作方式与执行通道结合目标、能力、上下文和可用性选择，可随发现调整。同一个任务可在执行开始时就采用多 Agent，
原生 Agent 和 Workbench 可单独或混合使用，不要求两种通道都调用。
主 Agent 对齐目标、安排分工、回查决定结论的证据并整合交付；具体核验可委派，不要求主 Agent 重做所有检查。

| 需要 | 合适的起点 | 交接重点与收口依据 |
| --- | --- | --- |
| 直接检查即可完成 | 直接执行或单个执行者 | 保留必要检查，不为了角色齐全扩大任务 |
| 扩大资料或实现覆盖 | 并行分工 | 分开材料或产物归属，明确依赖，核对交界处 |
| 独立核查关键结论 | 交叉验证 | 同样的必要原材料、各自的证据和检查；分歧回源或复算 |
| 多约束取舍尚未确定 | 圆桌讨论 | 分别形成观点或共同梳理约束，再讨论真正改变决定的分歧 |
| 需要新方向或不同方案 | 头脑风暴 | 独立发散、共同探索或接续创意，再按目标、约束与可验证性筛选 |
| 方案已有但关键假设存疑 | 对抗性分析、独立方案比较 | 先准确描述方案，提出可复现反例或可区分候选的试验 |

调研可独立查证同一个关键主张，同时分头补不同来源；测试可在实现时按需求独立设计用例；
文档审计可分别核对需求与实现、术语与跨文档一致性；方案设计可比较各自形成的候选。
不同分工不自动形成交叉验证，关键结论要有重叠核查。人数与角色由具体缺口决定。

需要独立推导时不先给另一方答案；共同探索允许提前交流，设想标为待验证，不冒充独立核验。产物审查提供实际产物、版本和验收依据。各方保留必要的初始结果，
修订结论时说明新增证据或哪条论证改变了判断。角色名称、不同通道、不同模型和一致意见都不能替代证据。
核验者可以在独立归属内创建测试、脚本或报告，不同时修改被核验的共享产物。
修复默认交回原 owner；明确阶段交接、原 owner 已停止写入后也可移交。
关键疑点已处理，或后续轮次不能增加有用解释、来源、试验、候选或可执行选项时停止；仍缺材料的结论保持未知。

协作方式、方法、顺序、人数、轮次和交付形式是可调整的建议，用户指定流程、预算、平台限制及专业验收仍须遵守。
探索包交接问题、已知材料、待查项与预期产物即可，不要求先知道答案。早期可提出类比与不完整候选，
形成事实结论、选定方案或执行前核对影响判断的重要前提。

需要拆假设、处理认知偏差或选择验证方法时，可独立使用 `think` 或由 sub 按需引用。
源码入口为 [think Skill](../codex_adaptive_agents/assets/think/SKILL.md)，三份方法参考按需读取。
think 不要求派发代理，不要求把全部方法跑一遍；已有专业 Skill 继续负责对应领域的事实与执行。
初始化会将 think 安装到所选 Codex 目录的 `skills/think/`，一起纳入安装备份、冲突检查和回滚。
也可只阅读源码中的 think 使用方法；手动复制的版本不自动获得受管升级能力。

### 常用模式与方法起点

以下名称便于表达任务，方法可跳过、组合、调整顺序、替换或加入其他合适方法。它们不是新的命令参数、固定角色或必经步骤。

| 模式 | 可选方法起点 | 要补的缺口 |
| --- | --- | --- |
| 分析／调研 | 第一性原理、竞争解释、选择偏差、因果分析 | 前提、来源与解释是否站得住 |
| 设计／决策 | 旋转门、可逆性、事前验尸、敏感性分析 | 方向、取舍、失败条件和关键参数 |
| 头脑风暴 | 反向思考、第一性原理，也可用其他创意方法 | 产生不同方向、连接和候选，再筛选 |
| 执行探索 | 最小验证试验、可逆性检查 | 用少量实际行动检验关键未知 |
| 验收／审计 | 对抗性分析、独立复算、可证伪检验 | 缺陷、反例和承诺是否达成 |

例如“用 sub 共同脑暴这个方向，先记录假设，形成候选后再验证”，可直接交流而不强制独立首轮；
“独立核算这项数据”则需要在比较答案前自行推导。方法带来的新解释与候选也算有用增量，但不能改标为已证实事实。

### 有限再分工

子代理默认完成收到的工作包。主 Agent 在已有用户委派授权与宿主支持内，可以明确允许有限再分工，
交接时说明子包范围、产物归属、可用执行者和预算边界。派发前核对真实工具、并发与既有 owner，
父子包关系及实际标识写入现有 state／evidence，原负责人继续整合与验收；没有宿主能力就直接完成或向主 Agent 交接。
再分工不扩大外发、付费、权限或修改范围，不让多个负责人同时写同一产物。

协作方式、关联任务与所用方法写入 code-record 的 state；独立产物与原始来源放入 evidence。
追加复核只有发现新问题或补齐证据才可能有收益；记录复核发现、修正、总耗时和可获得用量，
不把 Agent 数量、讨论轮数或同意票数当作质量提升。

## Luna 五档怎么选

以下是试用的初始经验规则，不是模型能力或最低成本的已验证结论。只使用宿主当前支持的候选。

| 档位 | 适合的起点 |
| --- | --- |
| low | 明确机械操作，有范例与直接检查，几乎不需要在方案间取舍 |
| medium | 路径已清楚的局部任务，需要少量判断与边界核对 |
| high | 有多个合理假设或相互依赖的判断，验收依据明确 |
| xhigh | 多约束任务，多个决定相互影响，需要比较替代方案 |
| max | 少数有充分材料但仍需深入推演的任务；说明相较 xhigh 的具体需求 |

同一档位可以对应不同工作量。批量机械替换通常先用一次脚本和检查，不逐项开代理。
失败后先判断是方法、环境、材料还是模型能力问题；只有能力确实不足、任务复杂度变化时才升档。
不设“失败一次就升一档”或一律默认 max 的规则。

## Workbench 怎么调用

读取现有 `agent-workbench-dispatch` Skill，沿用其调用脚本、真实 schema、项目背景、
稳定请求 ID、关键事件等待和结果回读。它独立维护任务、模型配置和凭据，不在本项目复制。

先读取 tools/list，再查询 `workbench_list_agent_options`。用户指定模型时用实际返回的准确组合；
未指定时可以用该 Agent 已保存的有效默认，创建后回读实际 provider/model。
默认不可用时先报告配置问题，不擅自改到别的供应商。应用或连接不可用且用户未指定通道时，
从其余实际可用候选中选择，并在理由里写明；不为派发安装或启动新服务。

一个可写工作单元只有一个 owner。结果不明先回读同一任务，不把等待超时当失败；
确需换执行者时先确认原 owner 已停止写入，再用新工作包明确重新交接。
普通输出、任务已创建或执行方自称完成都不是验收依据。

## 执行记录

`code-record` 保存实际开始后的执行者与选择理由，不调用 Laya、不创建任务、不执行 state。
命令名与 code-route-v1 版本沿用旧接口，state 可记录任意场景的目标、材料和验收条件。
每个实质工作包用稳定 task_ref；生产记录中的执行标识与模型来自真实工具返回。
模拟材料只用 verification。输入最多 50 行、128 KiB；验证整批输入后才保存。

必需字段为 task_ref、state、executor、reason。state 是交接时的材料，reason 简要说明为何选这个通道。
alternatives 可写其他可行方案及未选原因，evidence 可引用工具回执或产物。

| executor.kind | 必需的实际执行字段 |
| --- | --- |
| main | model |
| native | model、execution_id=宿主返回的真实子任务标识；宿主未披露模型时明确填 unknown 并引用回执 |
| luna | model=gpt-6-luna、role=adaptive_luna_*、execution_id=真实子任务 ID |
| workbench | agent_id、provider_id、model、execution_id=真实 Workbench taskId |

下面仅是 Workbench 格式示例；占位值不能作为真实派发证据：

```json
{"task_ref":"fix-parser-v1","state":"目标：修复解析器空输入；边界：解析模块；验收：空与非空输入检查。","executor":{"kind":"workbench","agent_id":"<实际Agent>","provider_id":"<实际供应商>","model":"<实际模型>","execution_id":"<真实taskId>"},"reason":"用户指定的执行器已在工作台接入，材料与验收可完整交接。","alternatives":["主 Agent 可完成，但本任务遵循用户指定通道。"],"evidence":["<实际任务回执来源>"]}
```

```sh
python3.12 codex-adaptive-agents.py code-record \
  --project "<业务项目绝对目录>" --input "<实际执行JSONL绝对路径>" --purpose production
```

记录追加在业务项目 `.codex-adaptive-agents/routes/<任务标识哈希>/events.jsonl`，同内容重交不重复写入。
production 同时将项目路径登记到当前 Codex home 的 `codex-adaptive-agents/route-projects.json`，
供周报发现明确关联的项目；索引不复制任务正文，verification 不登记业务项目。
执行结束可再次提交原工作包并添加 outcome；旧记录保留。outcome.status 可为 accepted、needs_rework、
failed、cancelled 或 unknown；除 unknown 外必须提供 outcome.evidence，只有实际核验才能使用这些状态。
outcome 可以携带有来源的耗时、返工次数和用量；缺失保持未知。程序验证结构，不保证填写内容真实，
周报仍需回源核对。所有通道的记录与 Laya 预测分开，不能把执行成功直接当成选档正确。

## 代码任务的原生 Luna 旁路测试

保留 code-shadow-v1 输入和缓存协议；当前仅测试代码任务的原生 Luna 档位，其他场景、Workbench 与主 Agent 不硬套此协议。
Laya 不决定派发、权限、重试或验收，失败不影响执行与 code-record。非代码及跨通道预测待专门验证后再扩展。

### 旁路使用顺序

1. 主 Agent 整理目标、材料、绝对工作目录、归属、产物和验收依据。
   派发前保存工作包材料和宿主已确认支持的候选档位。
2. 在授权与宿主允许的范围内，主 Agent 直接派发并核对工具实际返回的角色。
   小任务可以直接完成，不为了收集样本委派。
3. 在原工作包记录中补充 actual_role，提交本批新增工作包给 code-shadow。
   使用非阻塞命令；缺少非阻塞能力时等原工作包完成再测试。Laya 不决定或延迟实际派发。
4. 按任务要求核验产物，再用既有 monitor.py event 关联 task_key 与实际证据。
   没有证据的判断保持未知；记录由 Agent 完成，用户无需手工填写。

工作包的目标、材料与验收必须足够明确。方法按需要采用：问题定位读取相关调用者并验证根因，
代码修改复用已有实现并检查受影响行为，跨模块功能验证接口和主要操作路径。
不要求每次全仓库扫描、固定角色组合、固定输出篇幅或全部方法。

### 合批旁路入口

Python 3.11+，从本地源码入口运行即可；无需先修改全局 Codex 配置。
旁路需要当前 Codex home 下已有的 laya-monitor，沿用其私有 Python 环境、固定模型和 tracking_v2。
不重新安装模型、改全局 Skill 或启动服务。

输入是 UTF-8 JSONL，每行一个工作包：

```json
{"task_ref":"fix-empty-input-v1","state":"目标：修复空输入导致的崩溃。边界：仅修改解析函数，接口不变。材料：调用方传入空列表时抛出异常。验收：空输入返回空结果，非空输入行为保持，运行对应边界检查。","efforts":["low","medium","high","xhigh","max"],"actual_role":"adaptive_luna_medium"}
```

上例只是格式示例。生产记录的 actual_role 必须来自实际已启动的原生任务；
模拟角色仅用于 --purpose verification，不能证明实际 Luna 调用。
state 使用派发前的冻结材料，不包含最终选择、任务结果或模型建议。
efforts 是本次实际可用候选，2 至 5 项，按模型支持情况填写；候选只有一项时不增加判断。
一个批次最多 50 个工作包、输入最多 128 KiB；推理 token 预算仍由既有 Laya 接口核对，超限会失败而非静默截断。

```sh
python3.12 codex-adaptive-agents.py code-shadow \
  --project "<业务项目绝对目录>" \
  --input "<冻结工作包JSONL绝对路径>" \
  --purpose production
```

技术链路测试使用 --purpose verification。没有本地监测时返回 SHADOW_UNAVAILABLE；
推理或记录失败返回 SHADOW_FAILED；这些状态不改变原任务，观察命令按 best-effort 返回。
输入错误和不兼容参数会拒绝，原任务仍按既有方式继续。

命令只启动本地监测，不执行任务提示词，不派发 Agent，不调用外部评分、不切换模型或权限。
实际角色只进入跟踪上下文和题级事件；Laya 仅收到工作包材料、候选和两个问题：
材料是否足够、推荐的推理档位。建议未被采用，decision_changed 始终为 false，不自动标注正确性。

每批记录保存在业务项目 .codex-adaptive-agents/shadow/，包含冻结材料、模型输入、
上下文、监测 receipt、结果与私有日志；按项目允许的修改范围加入忽略。
重复同一批次返回缓存，调换输入顺序不会重跑。不同派发元数据不能覆盖旧快照。
中断后已有快照而没有完整结果时返回 SHADOW_INCOMPLETE，先核对 receipt，不自动再次调用。
当前仅对完整批次去重，每批只放新增包，避免在不同批次重复旧任务。
